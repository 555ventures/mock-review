# One Vite per host: the package never loads its own copy of Vite

## Goal

The package must work when the host app's `vite` is a different physical copy from the one under
the package's own `node_modules` — the `npm link` layout, a nested install, or any layout where the
two realpaths differ. Today, a host that mounts `mockReview()` in its own `vite.config.ts` and runs
its own `vite` answers every `/__mock-review/*` route with HTTP 500 (`the ssr environment is not
runnable (no module runner)`), because the plugin narrows the host's SSR environment with vite's
`isRunnableDevEnvironment`, a bare `instanceof` against the package's copy of the class (spike S7).
`check` and `serve` started from the package's bin are immune today only because they create the
server from the package's copy too — which means they run a second Vite beside the host's plugins.
Done means: every runtime use of `vite` inside `src/` goes through one helper that resolves `vite`
from the host root; the SSR environment is narrowed by shape, not by class; a host whose vite is
not major 8 is refused with one clear line; and package-tier tests prove both the host-run plugin
mount and the bin path load the real config with two physical copies on disk.

## Contracts

```ts
// src/analysis/host-modules.ts (D3)
export type HostVite = {
  createServer: typeof import('vite').createServer
  version: string
}
/** `createRequire(<root>/package.json).resolve(specifier)`; throws Node's own error (code MODULE_NOT_FOUND) when absent. */
export function resolveHostModule(root: string, specifier: string): string
/** Resolves and imports the HOST's vite (cached per root). Throws when the host's vite major is not 8.
 *  Falls back to the package's own `import('vite')` with a stderr warning when the host has none. */
export function loadHostVite(root?: string): Promise<HostVite>

// src/analysis/vite-runner.ts (D2)
export type Runner = { import: (absPath: string) => Promise<unknown> }
export type RunnerContext = { root: string; viteVersion: string }
/** Duck-typed narrowing of an ssr DevEnvironment to the one method the package uses. */
export function runnerOf(env: unknown, ctx: RunnerContext): Runner
export function withRunner<T>(cwd: string, fn: (runner: Runner) => Promise<T>): Promise<T>
```

Error messages (literal, asserted by tests):

| Situation | Message (after the CLI's `mock-review: ` prefix where it reaches stderr) |
|---|---|
| ssr env has no `runner.import` | `the host's Vite ssr environment has no module runner (vite <version> at <root>) — mock-review needs one vite 8 in the host` |
| host vite major ≠ 8 | `mock-review needs vite 8 in the host; found vite <version> at <dir of vite/package.json>` |
| host has no vite (warning only, stderr) | `mock-review: vite is not resolvable from <root>; using the package's own copy` |

`check --json` surfaces the first two as its existing `{ kind: 'config', severity: 'error', file: 'vite.config.ts', message }` finding (the `withRunner` catch in `src/analysis/check.ts`, unchanged); `serve` surfaces them as exit 2 on stderr with no stdout.

## Behavior

- `serve` startup order after this spec: `ensureDesignFiles` → `loadHostVite(cwd)` → `createServer` → strip Vite's signal handlers → **runner probe (D4)** → `readConfigPort` → `listen` → portfile → URL on stdout. A probe failure exits 2 with one stderr line and writes no portfile.
- Host-run plugin mount (`mockReview()` in the host's `vite.config.ts`, host's own `vite` binary, package linked from outside the host): the host's copy creates the server; `runnerOf` accepts its ssr environment by shape, so every `/__mock-review/*` route answers as on a single-copy host. Today this path is HTTP 500 on every such route.
- `check`/`serve` from the package's bin on the same host: `loadHostVite` imports the host's copy, so the server, the host's plugins (which import `vite` from their own realpath) and the package now share one instance. This path was already green (both server and guard came from the package's copy); the change removes the second Vite instance that path used to create.
- Under a host with no `vite` at all, `loadHostVite` warns on stderr once per root per process and uses the package's own copy; stdout stays clean (JSON verbs print only JSON).
- Nothing in this spec changes `optimizeDeps.include`, `resolve.dedupe`, the entry HTML, roles, or any served route.

## Assumptions (escalation triggers)

## Rationale

The bug is a class-identity problem, not a configuration one. Vite's `isRunnableDevEnvironment` compares against the `RunnableDevEnvironment` class of whichever copy of vite exported it. When the package's bin imports `vite` by bare specifier, Node resolves it relative to the package's own files, while the host's `vite.config.ts`, its plugins, and the dev server class all come from the host's copy. With `npm link` (or any nested install) those are two realpaths and two classes, so the guard is false for a perfectly good environment. The planning session first assumed the bin path (`check`/`serve`) was the victim and that the failure was swallowed into `NULL_CONFIG`; spike S7 falsified both. The bin path creates the server from the package's copy too, so guard and class agree there, and `configFor` already wraps only `loadConfig`. The real victim is the host-run plugin mount — `mockReview()` in the host's `vite.config.ts` under the host's own `vite` — which answers HTTP 500 on every `/__mock-review/*` route, with a stack that names the host's bundled config file rather than the plugin. The design still stands for both paths: the plugin path needs the shape-based narrowing; the bin path needs `loadHostVite` so the package stops running a second Vite beside the host's plugins (spike S6: `@vitejs/plugin-react` and `@tailwindcss/vite` import `vite` at runtime from their own realpath).

Two independent fixes were considered and both are taken. Duck typing (`runner.import` is a function) removes the class dependency for the narrowing itself. Loading vite from the host root removes the second copy for everything else (`createServer` in `check` and `serve`), which is the real fix: a package that is a Vite *plugin* must run inside the host's Vite, never bring one. Keeping only one of the two would leave either the narrowing or the server on the wrong copy.

The failure split matters for the pipeline that consumes this tool: a spec plugin reading `check --json` must be able to tell "your config is wrong" from "your install is broken". So `NULL_CONFIG` is reserved for config problems, and the runtime problem throws with the vite version and the root in the message. `serve` probes once at startup so the person who started it sees the refusal on their terminal, before any URL is printed or a portfile written.

The fallback for a host with no vite is deliberately soft (warning, use the package's copy). It matters for the fixture-style hosts in tests and for any host that happens not to import from `vite` in its config; hard-failing there would be a regression for no gain. A host on vite 9 or 7 is a hard error because the Environment API shape the package relies on is only spiked on 8.

Collision closure (`--literal isRunnableDevEnvironment`): the two hits under `dist/` (`dist/analysis/vite-runner.js`, `dist/server/plugin.js`) are waived — `dist/` is the committed release artifact, rebuilt only at release (D19 of specs/20260915/01), never in a build batch; the queued release step after this spec closes regenerates them. The `.claude/rules/spec-pipeline.md` and `src/` hits are File Plan rows.

Fragile points: the fake-server unit tests (AC-3/AC-4) exercise the middleware directly and depend on the exact fields `configureServer` touches; the two-copies package test runs a real server and is slow. The source-ban test is the guard that keeps this from regressing when the next feature needs a Vite export.
